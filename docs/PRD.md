# Product Requirements Document (PRD)
**Project Name**: Lenny Growth Assistant
**Date**: August 2026

---

## 1. Executive Summary
The Lenny Growth Assistant is an AI-powered orchestration platform designed to help users interact with the vast repository of Lenny's Podcast transcripts. Rather than acting as a simple Q&A bot, the product functions as a true "Agent" capable of dynamically deciding the intent of a user's query—be it retrieving factual advice, generating viral essays, or writing code components—and executing the request flawlessly.

## 2. Problem Statement
Current generative UI products either lack grounding (hallucinating answers) or lack formatting flexibility (dumping massive blocks of unstyled text). Users wanting to extract actionable insights from Lenny's transcripts currently have to manually search, copy, paste, and format the data using disparate tools.

## 3. Product Vision
To build a singular, agentic interface where users can query Lenny's transcript database and receive context-grounded, beautifully formatted artifacts (Markdown essays, React code blocks, Q&A summaries) in a seamless, unified workspace.

---

## 4. Feature Requirements

### 4.1 Multi-Agent Orchestration (The "Pi" Agent)
- **Requirement**: The system must intelligently route queries to the correct specialized function ("Skill").
- **Acceptance Criteria**: 
  - A zero-shot intent classifier evaluates the user's prompt.
  - Queries are routed to exactly one of three skills: `qa_skill`, `ship30_skill`, `code_skill`.
  - The routing logic must bypass the conversational RAG pipeline when the user explicitly requests an essay or a code snippet.

### 4.2 Dynamic LLM Toggling
- **Requirement**: The backend must support multiple LLM providers for cost and latency optimization.
- **Acceptance Criteria**: 
  - Developers can switch between local (`Ollama`) and remote (`OpenAI`) execution by modifying a single `.env` variable (`LLM_PROVIDER`).
  - The integration must be completely transparent to the frontend application.

### 4.3 Interactive Artifact UI
- **Requirement**: The frontend must safely and beautifully render code and markdown generated by the assistant.
- **Acceptance Criteria**: 
  - Implementation of a split-screen Artifact Viewer that dynamically slides into view.
  - Integration of `react-markdown` and `react-syntax-highlighter` to provide real-time formatting.
  - Support for multi-tab rendering (Preview vs. Code).

### 4.4 Persistent Sessions
- **Requirement**: Users must be able to maintain conversational state and revisit past interactions.
- **Acceptance Criteria**: 
  - The PostgreSQL database must store `sessions` and `messages`.
  - The frontend must auto-refresh the sidebar after sending a message to a new session.
  - Past messages must be recursively fed into the LLM context to enable conversational memory.

---

## 5. Non-Functional Requirements
- **Performance**: The frontend must remain unblocked during artifact generation. The backend must use asynchronous HTTP clients (`httpx`).
- **Security**: Database interactions must prevent SQL injection via parameterized queries or robust ORM handling (via Supabase client/asyncpg).
- **Design**: The system must adhere to the "Impeccable" UI/UX style guide, ensuring high contrast, clean typography, and zero visual clutter.

## 6. Success Metrics
1. **Routing Accuracy**: >95% of queries correctly classified into the appropriate Skill pipeline.
2. **Latency**: Sub-second UI updates, with TTFB (Time to First Byte) under 2 seconds for local inference.
3. **Engagement**: Increased interaction with the Artifact Viewer for long-form content generation.
